# 点格棋

直接打开 `index.html`，或在此目录运行 `python3 -m http.server 8000` 后访问 http://localhost:8000 。无依赖、无构建、无外部请求。

- 本地双人对弈，默认 5×5，支持 1–12 行／列；应用新尺寸会清空棋盘。
- 得分后必须继续落子；允许放弃立即得分的机会。悔棋撤销一条边。
- URL hash 保存版本、尺寸和完整落子序列。复制完整网址可恢复并继续悔棋。
- AI 在独立 Worker 内使用 UCT MCTS；使用收格、安全边结构、开口送格代价和留二／留四启发式引导探索；保留少量随机探索，较大棋盘估计仍可能有偏。
- 所有局面都交替推进 MCTS 和精确证明，没有剩余边数门槛。精确任务按候选组轮转、按深度逐步加深，使用可暂停递归保存批次之间的进度。不会因单个候选未完成而丢弃其他候选的证明。
- 胜率使用胜 1、平 0.5、负 0 的平均值，始终从当前待落子方角度计算。非精确结果是搜索估计，并非校准的真实概率。
- 分析持续运行直到关闭或所有候选分差完全精确。MCTS 树最多保留 40,000 个节点；证明缓存最多约 60,000 个局面，分批淘汰旧条目。已精确的根候选停止模拟，算力用于尚未解决的候选。落子、悔棋和重新开启分析复用同尺寸棋盘的证明缓存；MCTS 统计在新分析请求中重新开始。
- 未访问的候选显示 —；深绿表示较高估值，鲜红到近白的三种描边表示前三名。键盘 Tab / Enter / Space 可落子。

验证：`node test.js`。

## 对称性与色阶

正方形使用 8 种旋转／反射，非正方形矩形使用 4 种。MCTS 在每个节点只保留维持当前已落边布局不变的变换，把等价候选合为一个分支，共享胜率与访问次数；非对称局面自动退化为独立候选。精确搜索还使用旋转／反射规范化的局面键共享缓存。历史边的颜色不影响未来合法着法，因此对称判断只看边是否存在；当前行动方和已有分数仍由搜索状态保留。

绿色使用当前候选之间的相对色阶，深绿更优；至少使用 8 个百分点的映射跨度，避免放大极小的噪声。数字仍为原始胜率估计。对称落点显示同一份统计，次数不能逐格相加；悬停可查看共享落点数量。

## 启发式与残局求值

- 搜索分支使用渐弱的启发式偏置；模拟有 6% 概率均匀探索，所有合法候选都有机会被访问。
- 通过未画公共边构建格子连接图，识别长链、闭环和已经打开的链环。
- 没有安全边时，按打开的二度格子走廊长度估计送格代价；安全边会按延长／连接脆弱走廊的程度降低优先级。这些是经验评分，不作精确剪枝。
- 留二／留四是否值得，比较剩余残局价值和让子成本；不强制永远保持控制权。
- 对仅含未打开长链（至少 3 格）、环（至少 4 格），以及至多一个可识别打开组件的局面，可直接计算未来最优分差。组件级递推同时比较全部收取与保持控制；短链、分叉、多处同时打开等未覆盖结构交给一般搜索。
- 精确值用于缩短模拟和加速 minimax；每个候选独立标记证明状态；只有全部候选都精确时才结束整个分析。

## 三行分析标注

依次显示胜率、预计最终净胜格数、探索次数。净胜格数始终从当前待落子方视角计算，包含已有分数；正数领先，负数落后。未证明时显示模拟平均最终分差；得到严格分差上下界后，将估计限制在该区间内；完全精确时显示最优分差。未探索候选显示 —。搜索仍以胜率为主要目标，新增分差不改变搜索目标；前三描边按胜率降序排列，胜率相同时按预计净胜格数降序排列，两项均相同则并列。

## 渐进证明

- 每批约 10ms 用于 MCTS、50ms 用于证明，然后让出 Worker 事件循环。精确搜索逐层加深（每轮加 2 条边），深度上限处仅保留严格上下界，绝不把模拟估值当作证明。
- 缓存保存当前行动方未来得分差的上下界与已搜索深度；对称规范化后可跨落子、悔棋复用，不受历史比分或边颜色影响。根据同方继续落子／换方正确传播界限。无法超越已知下界的分支可跳过。
- 胜率后 `*`：胜负已证明（100% 必胜／0% 必败），分差仍是估计。胜负和分差都精确时在次数前显示 `✓`；平局的精确分差为 0。
- 悬停候选可查看证明状态、严格分差区间及模拟／证明次数。第三行次数是该候选组的模拟访问与证明节点检查之和；对称落点共享统计，不能逐格相加。
- 顶部显示已证明胜负、已精确分差的落点数量。每次请求带独立编号，界面忽略旧棋局结果；暂停取消后续批次但保留缓存。
- 这是完备 minimax 的渐进搜索方式，不保证大棋盘能在实际可接受时间内求解；内存上限引起的缓存淘汰也可能增加重复工作。

## 胜负优先

证明阶段采用两条调度队列：尚未证明胜负的候选与已证胜负但分差未精确的候选。两条队列均非空时，每 10 个证明调度槽中 9 个用于胜负、1 个用于分差；某队列为空时预算全部交给另一队列，各队列独立轮转以避免候选被饿死。这是调度比例，不是严格的 CPU 时间比例。

胜负搜索使用整数分差阈值窗口：先证明是否至少赢 1 格；如果已知无法获胜，再证明能否至少打平。达到相应上下界即可剪枝，无需先解出完整分差。窄窗口缓存与完整分差搜索的深度记录分开，保证先前的胜负剪枝不会妨碍后续分差证明。MCTS 在仍有胜负未证候选时优先模拟这些候选；模拟中胜率和分差来自同一批样本，统计均值本身开销很小。
